# План: от выгрузки к базе с поиском

Версия 0.1 · 10.11.2026 · Основа — `docs/analiz-idei.md`.

Этапы идут по порядку, но этапы 2 и 3 можно вести параллельно. Размеры — относительные: S — часы, M — дни, L — недели работы одного человека. Календарных сроков не обещаю.

## Этап 0. Решения

- Ответить на шесть вопросов из `docs/analiz-idei.md`, раздел 9.
- Написать положение о вики на одну страницу: принципы из `wiki/README.md`, процедура исправлений, политика персональных данных (без контактов, только публичные деловые роли).
- **Готово, когда:** ответы записаны в `docs/decisions.md` или в README, и у каждого решения есть дата.

## Этап 1. Сбор и проверка признаков

- Выгрузка сделана для октября и ноября 2026 (`tools/hn_hiring_export.py`).
- Ввести ежемесячный запуск при выходе нового треда: вручную или по расписанию.
- Выполнено: 60 постов (две выборки по 30) размечены тремя независимыми оценщиками вместо ручной разметки; это ограничение описано в `docs/tochnost-priznakov.md`. Точность считает `tools/eval/score.py` по эталону `tools/eval/gold.json`.
- **Готово, когда:** точность по каждому признаку известна и записана. Предлагаю порог 90% для «удалённо», «зарплата» и «роль». Если признак ниже порога, переписываем правило и проверяем заново.

## Этап 2. Отбор компаний

- Стартовый список: компании, которые публиковались в двух и более выпусках. Сейчас это 48 доменов из 142 у ноября.
- Фильтр «стартап» по решению из этапа 0: возраст, независимость, наличие публичного продукта.
- Дедупликация: один домен — одна фирма. Ссылки на сервисы подбора сопоставляем с компанией по названию из поста, вручную.
- **Готово, когда:** список на 100 компаний. У каждой записи есть поле «прошла / не прошла критерий» и причина.

## Этап 3. Карточки

- Шаблон и схема описаны в `wiki/README.md`. Пилот — 12 карточек.
- Расширение: 50 карточек, затем 100. Выбирать по сферам, а не по алфавиту.
- Для каждой карточки: сайт компании и второй независимый источник (торговый реестр, GitHub, пресса). Заявления компании выносятся в отдельный раздел.
- Чек-лист перед публикацией: ссылки открываются; нет контактов; у каждого числа есть источник; заявления помечены; дата проверки проставлена.
- **Готово, когда:** 50 карточек прошли чек-лист, и у половины есть второй источник для организационных данных (год основания, штаб-квартира).

## Этап 4. Структурированная база

- Собрать YAML-шапки всех карточек в единый CSV и JSON.
- Валидатор: обязательные поля, формат дат и URL, отсутствие e-mail и телефонов (регулярными выражениями).
- Фильтры по полям: сфера, технологии, формат, зарплата, локация, дата проверки.
- **Готово, когда:** валидатор проходит на всех карточках, а фильтры на 10 тестовых запросах дают тот же результат, что ручной поиск.

## Этап 5. Поиск: фильтры, полнотекст, RAG

Поиск строится в три слоя. Каждый следующий слой включается, только если предыдущий не справляется.

1. **Структурированный запрос.** Вопросы с числами и условиями (сколько, средняя, сортировка по зарплате) решаются таблицей: SQL или DuckDB поверх CSV.
2. **Полнотекстовый поиск (BM25)** по разделам карточек. Точные слова — названия технологий, ролей, продуктов — важнее смысла.
3. **Векторный поиск (RAG).** Чанки — разделы карточек, а не куски текста по символам. Каждый чанк несёт метаданные: id, сфера, дата проверки, ссылка на источник.

Правила ответа:
- ответ всегда содержит цитату (раздел карточки и ссылка на источник);
- если поля нет, ответ — «в базе этого нет», без догадок;
- заявления компаний в ответе помечаются как заявления.

**Оценка.** Тестовый набор из 50–100 вопросов с эталонными ответами. Метрики: доля верных ответов, доля ответов с правильной ссылкой, доля корректных отказов, задержка и стоимость одного запроса.

- **Готово, когда:** на тестовом наборе не меньше 85% верных ответов, не меньше 90% корректных отказов и ссылка в каждом ответе.

## Этап 6. Машиночитаемость для агентов

- Файл `llms.txt` с описанием базы и ссылками на карточки (соглашение llms.txt).
- JSON-LD на страницах карточек: schema.org `Organization`, `SoftwareApplication`, `JobPosting`.
- Проверка гипотезы о спросе: 2–3 недели наблюдений за обращениями к страницам и API. Смотрим, кто и как читает, какие вопросы задают.
- Опционально: MCP-сервер с инструментами поиска. Делаем только если гипотеза подтвердилась.
- **Готово, когда:** есть данные о спросе, и решение «делать MCP или нет» принято по этим данным.

## Этап 7. Поддержка и доверие

- Ежемесячный цикл: новый тред → выгрузка → обновление карточек → короткий отчёт об изменениях (журнал).
- Процедура исправлений: заявка → проверка источника → правка → запись в журнале. Срок ответа предлагаю 14 дней.
- Устаревание: карточки старше трёх месяцев помечаются; старше шести — скрываются из поиска до обновления.
- Снятие карточки: по запросу компании, если в ней есть неточность, которую не удаётся подтвердить.
- **Готово, когда:** два цикла обновления прошли с документированными исправлениями и без жалоб, которые остались открытыми дольше срока.

## Этап 8. Расширение: продукты, сервисы, модели

- Новый тип сущности: «продукт или сервис» с полями возможностей. Это входы и выходы, способ доступа (API, SDK, MCP), аутентификация, тарифы (заявлено или проверено), ограничения (лимиты, регион данных), дата проверки.
- Связи: компания выпускает продукт; продукт использует технологию; компания нанимает на роль; роль требует технологию; продукт интегрируется с продуктом.
- Заявления провайдеров помечаются так же, как в вики. Бенчмарки — только со ссылкой на методику.
- **Готово, когда:** 20 карточек продуктов проверены и хотя бы один запрос от агента или разработчика решён лучше, чем без базы.

## Риски

| Риск | Мера |
|---|---|
| Персональные данные (контакты, основатели) | правило «без контактов»; минимизация полей; консультация юриста до этапа 3 |
| Права на базу и на тексты сайтов | короткие цитаты; проверка robots.txt и условий; выбрать лицензию текста до публикации |
| Ошибка о компании | процедура исправлений; пометки «заявлено»; журнал изменений |
| Галлюцинации в RAG | цитаты в каждом ответе; отказ при пропусках; оценка на тестовом наборе |
| Источник меняет правила или API | второй источник на этапе 2 |
| Ручная проверка не масштабируется | ограничить сферу; автоматизировать признаки; проверять выборочно, например 20% карточек в месяц |
| Регулирование ИИ в подборе людей | не ранжировать кандидатов; продукт работает с компаниями и вакансиями |

## Следующие три шага

1. Ответить на шесть вопросов из `docs/analiz-idei.md` (раздел 9). От них зависят этапы 2 и 3.
2. Проверить 20–30 постов вручную (этап 1) и сравнить с эталоном трёх оценщиков: это закроет главное ограничение измерения точности.
3. Выбрать одну сферу и довести её до 50 карточек (этап 3). Лучший кандидат — ИИ-инфраструктура и dev tools: это самая большая группа в выборке (8 из 12 компаний), и у них понятные описания продукта на сайтах.
