# Пересечения и параллели

Версия 0.1 · 10.11.2026 · Дополняет `docs/analiz-idei.md`.

Здесь собраны существующие базы, стандарты и сервисы, которые пересекаются с идеей вики по фирмам из «Who is hiring?». Отдельный раздел — про поиск, в котором помимо людей ищутся сервисы, модели и агенты.

Сведения о сторонних сервисах даны по их существованию и роли. Условия использования, актуальность и точность каждого проверяются перед использованием (см. раздел 6).

| Levels.fyi, Glassdoor | зарплаты и отзывы | данные часто самонаполняемые, не из постов | сравнение зарплатных вилок с данными треда |
| Wappalyzer, BuiltWith | технологии сайта (стек по сайту) | определяют стек по признакам в коде страницы, а не по вакансиям | автоматическое поле «технологии» с пометкой источника; проверить лицензию |
| GitHub и Hugging Face | метрики открытого кода и моделей: звёзды, загрузки, релизы | метрики популярности, а не качества | объективные подтверждения «open source» |
| ClinicalTrials.gov и аналогичные реестры | клинические исследования | только для медицинских компаний | проверка заявлений медтеха (например, Paradromics) |
| schema.org (JobPosting, Organization) | стандарт разметки для вакансий и организаций | это разметка, а не база | стандарт для машиночитаемых страниц карточек |
| llms.txt и MCP | файлы и протоколы, которые помогают ИИ-агентам читать сайты и вызывать инструменты | не база данных | способ сделать базу доступной агентам |
| Каталоги MCP-серверов и API | «машины» как объекты поиска: что умеют, как вызываются | ориентированы на инструменты, а не на компании | образец карточки «возможностей» продукта |

## 2. Что важно в ключевых аналогах

**Википедия.** Главные для нас правила — нейтральность, проверяемость и значимость. Из-за них в Википедии не пишут о компаниях, если о них нет независимых источников. Это тот же механизм, который нужен вики по стартапам: без независимого источника карточка не публикуется. Ещё важнее правило о конфликте интересов: представители компании не должны править её статью напрямую.

**Викиданные.** Здесь каждая сущность имеет идентификатор и набор свойств (отрасль, штаб-квартира, год основания, работодатель). Это почти та же схема, что YAML-шапка карточки. Идея: связать каждую карточку с сущностью Викиданных, когда она есть. Так удобно устранять дубликаты (одна компания под разными названиями) и подтягивать проверенные реквизиты. Данные Викиданных распространяются по лицензии CC0.

**Корпоративные вики и публичные handbook.** Корпоративная вики хранит знания одной организации, а наш проект — знания о многих организациях снаружи. Пример PostHog показывает, что компания может публиковать внутренние правила работы и зарплаты. Для вики это ценный сигнал, но и источник данных, который стоит пометить как «заявления компании».

**Crunchbase и аналоги.** Здесь на первом месте финансирование: раунды, инвесторы, оценка. Для нашей задачи это вторично. Но поле «финансирование» полезно для фильтров: например, «компании после раунда Series A, которые нанимают инженеров». Источником такого поля должна быть не пресса, а проверяемая запись.

**Агрегаторы Hacker News.** gethnjobs.com и hnwork.app упомянуты в шапке треда как места для поиска работы. Это прямые конкуренты в части «поиска по треду», но не в части проверенных карточек компаний. Пользователь, который хочет сравнить фирмы, сейчас вынужден читать посты вручную. Здесь отличие нашего продукта.

**Sumble.** Это самый близкий коммерческий аналог по замыслу: граф компаний, команды, стек, проекты, найм. Отличия: Sumble ориентирован на продажи; наш проект — на соискателей и открытость. Полезный урок: их подход к полям «сигналы» и «проекты» (например, внедрение ИИ или миграция в облако) стоит перенять как поля карточки с пометкой источника.

**Реестры компаний.** Торговые реестры дают то, чего нет на сайтах компаний: юридическое название, номер регистрации, суд, руководство. Пример из выборки: Proxima Fusion GmbH с номером HRB 283423 в Мюнхене. Номер можно проверить самостоятельно, и это хороший образец для поля «организация».

**Публичные API вакансий.** У части сервисов подбора есть публичные API для страниц вакансий. Если они доступны и разрешены условиями, это надёжнее, чем разбор HTML. Но сначала нужно проверить условия использования каждого сервиса и актуальность данных.

**Стандарты разметки.** schema.org описывает вакансии (JobPosting) и организации (Organization). Поисковики используют эту разметку для показа вакансий, а значит, она уже знакома инструментам. Если сделать страницы карточек с JSON-LD, их можно будет читать и поисковикам, и агентам без дополнительного формата.

## 3. Другая сторона треда: «Who wants to be hired?»

Парный тред — зеркало основного: специалисты публикуют себя. Вместе они образуют двусторонний рынок. Но соискатели — это персональные данные в высокой степени. Публиковать их в вики без явного согласия нельзя, а согласие ещё нужно проверить на соответствие GDPR.

Поэтому рекомендация такая: в вики не включаем соискателей. Если понадобится сопоставление «кандидат — вакансия», это отдельный продукт с согласием, правом на удаление и аудитом. Такой продукт попадает в зону высокого риска по EU AI Act (см. `docs/analiz-idei.md`, пункт 8 в минусах).

## 4. Поиск не только людей: машины, компьютеры, ИИ

### 4.1. Что может означать «искать машины»

Под «машинами» можно понимать три разных вещи:

1. **Сервисы и продукты** (SaaS, API, инфраструктура): кто что делает и с чем интегрируется. Это самый реалистичный вариант.
2. **Модели и агенты** (языковые и табличные модели, агенты, MCP-серверы): что умеют, как их вызвать, сколько стоят, какие у них ограничения.
3. **Вычислительные ресурсы** (облака GPU, кластеры, суперкомпьютеры): где находятся, сколько стоят, какие у них лимиты.

В выборке видны первые два типа: LiveKit, Reducto, Mastra, Prior Labs, Zed, VictoriaMetrics. Третий тоже присутствует: CoreWeave публикует вакансии по вычислительной инфраструктуре, Proxima Fusion нуждается в HPC-кластерах. Но третий тип сложнее поддерживать, потому что цены и лимиты меняются часто.

### 4.2. Минимальная схема сущностей

| Сущность | Ключевые поля | Связи |
|---|---|---|
| Организация | название, сайт, сфера, юрлицо, год, страна, источники | выпускает продукт; нанимает на роль |
| Продукт или сервис | организация, категория, входы и выходы, доступ (API, SDK, MCP), аутентификация, тарифы (заявлено и проверено), ограничения, регион данных, дата проверки | использует технологию; интегрируется с продуктом |
| Модель | разработчик, лицензия или веса, контекст, языки, ограничения, бенчмарки со ссылкой на методику | доступна через продукт |
| Вакансия | организация, роль, локация, формат, зарплата из поста, дата поста | требует технологию |
| Технология | название, категория, открыта или нет | — |

Минимальный набор полей для продукта — это то, что агент или человек спросит, прежде чем выбрать инструмент: что принимает, что возвращает, как авторизоваться, сколько стоит, где хранятся данные, когда проверено.

### 4.3. Как RAG работает здесь и где не работает

**Как работает.**

- Чанки — разделы карточки («Кто они», «Технологии», «Кого ищут»), а не куски текста по символам. Так смысл не рвётся на середине.
- Каждый чанк несёт метаданные: id, сфера, дата проверки, ссылка на источник.
- Гибридный поиск: BM25 для точных слов (названия технологий и ролей) и векторный поиск для смысла. Для технических терминов точное совпадение часто важнее смысла.
- Фильтры по метаданным до поиска: например, только карточки, проверенные за последний месяц.
- Ответ с цитатой: раздел карточки и ссылка на источник. Ответ без цитаты не выдаётся.

**Как отказывать.** Если поле «не указано», система пишет, что в базе этого нет. Она не должна придумывать год основания или сумму зарплаты. Такой отказ — часть продукта, а не сбой.

**Где RAG не нужен.** Счёт, среднее, сортировка и пересечения условий решаются структурированным запросом. Пример: «сколько удалённых вакансий на Rust с зарплатой» — это SQL по CSV, а не RAG. Смешанный вопрос решается в два шага: сначала фильтр по полям, потом RAG по найденным карточкам.

**Оценка.** Тестовый набор вопросов с эталонными ответами, метрики — в `docs/plan.md`, этап 5.

### 4.4. Машиночитаемость для агентов: польза и риски

**Польза.** Агент выбирает инструмент по возможностям, а не по рекламе. Он быстрее находит подходящие вакансии или продукты. Каждый его ответ можно проверить по ссылке.

**Риск 1: инъекции через текст.** Сайты и карточки содержат текст, который агент может принять за инструкцию. Пример из выборки: на сайте Reducto есть раздел «Setup for agents» с инструкциями. Правило для системы: текст карточек и страниц — это данные. Инструкции, найденные внутри данных, не выполняются.

**Риск 2: отравление базы.** Компания может написать в карточке то, что нужно агенту, а не то, что есть на самом деле. Защита: заявления помечаются, сверяются со вторым источником, в журнале видно, кто и когда что изменил.

**Риск 3: ложный спрос.** Гипотеза «агенты будут пользоваться базой» не подтверждена. Её нужно проверять логами обращений (этап 6), а не предположениями.

### 4.5. Что уже делают другие

- **Корпоративные вики с ИИ-поиском.** Notion и Confluence с ИИ-функциями работают по тому же паттерну: поиск по документам с ответом и ссылкой. Наш корпус — внешний, то есть публичные сайты и посты.
- **Каталоги MCP-серверов и API.** Здесь «машина» — это объект поиска: описание возможностей плюс способ вызова. Наши карточки продуктов — человекочитаемый вариант того же.
- **Сайты, которые обращаются и к людям, и к агентам.** Reducto (раздел для агентов, SDK, CLI и MCP-сервер) и LiveKit (SDK и документация для агентов) показывают, что поставщики уже сами делают описания для машин. Значит, спрос со стороны поставщиков есть.

## 5. Итоговая карта пересечений

- **Нормы и правила** — из Википедии: нейтральность, источники, значимость, конфликт интересов.
- **Структура и идентификаторы** — из Викиданных и schema.org.
- **Найм и стек** — из постов треда, ATS и Wappalyzer-подобных инструментов.
- **Деньги и инвесторы** — из Crunchbase и аналогов, как необязательные поля.
- **Юридические факты** — из торговых реестров.
- **Открытый код и модели** — из GitHub и Hugging Face.
- **Поиск и ответы** — RAG по разделам карточек, фильтры по полям, отказы при пропусках.
- **Машиночитаемость** — llms.txt, JSON-LD, каталоги возможностей, MCP как опция.

## 6. Что я не проверял

- Точность признаков в выгрузке. Есть только оценка по эвристикам; ручная проверка запланирована (`docs/plan.md`, этап 1).
- Условия использования сервисов, которые упомянуты здесь (gethnjobs.com, hnwork.app, Wellfound, Crunchbase, ZoomInfo, Levels.fyi, Glassdoor, Wappalyzer, BuiltWith, OpenCorporates и др.). Я упоминаю их по существованию и роли. Перед использованием нужно проверить условия, актуальность и лицензии.
- Публичные API ATS: доступность, условия и актуальность. Тоже нужно проверить.
- Правовые режимы (GDPR, EU AI Act, охрана баз данных) — это ориентиры для обсуждения, а не юридическое заключение.
